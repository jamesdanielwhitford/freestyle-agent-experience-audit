Modal (modal.com) - Feature Research

1. VM Startup Speed / Cold Start Times

Modal is built around very fast cold starts. Container cold starts are typically in the range of 1-3 seconds for pre-built images (using modal.Image). Modal caches container images aggressively. When containers are "warm" (kept alive via keep_warm or container_idle_timeout), invocations are near-instant (sub-100ms). The platform is specifically architected to minimize cold starts compared to AWS Lambda or GCP Cloud Run. Exact published numbers vary by workload, but Modal has claimed sub-second cold starts for many workloads in blog posts.

2. Boot Disk Access

Modal containers run on ephemeral scratch disks by default. Modal provides modal.Volume (a persistent, network-attached filesystem that can be mounted into containers) and modal.CloudBucketMount for S3/GCS access. There is no persistent local boot disk in the traditional VM sense - the container filesystem is ephemeral per run.

3. Reboot Support

Modal does not offer traditional VM reboots. It is a container/serverless model. You can restart a container by re-invoking a function, but there is no "reboot" primitive. Long-running containers can be configured with keep_warm.

4. VM Forking Capability

Modal does not expose VM/container forking (like fork() at the infrastructure level) as a user-facing primitive. This is not a documented feature as of my knowledge cutoff.

5. Full Linux Support

Yes. Modal containers run on Linux (Debian/Ubuntu-based). You can install arbitrary system packages via modal.Image.apt_install(), run arbitrary binaries, and have full root access inside containers. You choose the base image (e.g., debian:bookworm, ubuntu:22.04, or pre-built ML images).

6. GPU Support

Yes, extensive. Modal offers: - NVIDIA A10G, A100 (40GB and 80GB), H100, T4, L4 GPUs - Multi-GPU configurations - GPU access is specified per-function via gpu="A100" or gpu=modal.gpu.H100() - Billed per second of GPU use - H100s are available (SXM and PCIe variants)

7. Language Support

Modal's SDK is Python-first. The core interface is a Python SDK (pip install modal). However: - You can run any language inside containers (Node.js, Go, Rust, Ruby, etc.) by installing them in the image - There is a REST API / webhook support so non-Python callers can trigger Modal functions - As of late 2024/early 2025, Modal added support for running web endpoints that any language can call - Native SDKs for languages other than Python are not officially published

8. MCP Server Availability

Modal has published an MCP (Model Context Protocol) server. As of early 2025, Modal released tooling to deploy MCP servers as Modal apps, making it easy to host MCP servers serverlessly. There were blog posts and docs about this. Whether Modal itself exposes an MCP server for interacting with the Modal platform (as opposed to hosting your own) is less clear from my training data.

9. llms.txt Availability

Modal has an llms.txt file at https://modal.com/llms.txt - this became a common practice in 2024-2025 for AI-friendly documentation discovery. I do not have confirmed details on its exact contents, but Modal is an AI-infrastructure company and was likely an early adopter.

10. Multi-tenant Git Support

Modal does not have a built-in Git hosting or multi-tenant Git feature. It integrates with Git via standard CI/CD (GitHub Actions, etc.) and you can deploy from a Git repo. There is no native Git server or multi-tenant Git namespace feature analogous to what you'd find in a platform like Gitpod or Coder.

11. Serverless Runs

Yes, this is Modal's core offering. Functions decorated with @app.function() run serverlessly - scale to zero when not in use, scale out to thousands of parallel containers automatically. Supports: - function.remote() for synchronous calls - function.spawn() for async/fire-and-forget - function.map() for parallel fan-out over iterables - function.starmap() for parallel fan-out with multiple args - Scheduled runs via @app.function(schedule=modal.Period(hours=1))

12. Deployments

Yes. modal deploy deploys an app persistently (web endpoints stay up, scheduled functions remain active). Contrast with modal run which is ephemeral. Deployed apps get stable URLs. Modal also supports: - Web endpoints (@app.function(web=True) or @modal.web_endpoint) - ASGI/WSGI apps (FastAPI, Django, etc.) via @app.function(web=True) with asgi_app - Secrets management for deployed apps - Named deployments with versioning

13. Free Tier

Modal has a free tier: - $30/month in free credits for new users (as of 2024) - No credit card required to start - Free tier includes CPU and GPU compute credits - The free allowance resets monthly for some tiers

Exact current free tier details may have changed - this is worth verifying at modal.com/pricing.

14. Agent Discoverability

Modal supports discoverability for AI agents in several ways: - Functions can be exposed as web endpoints with stable URLs - Modal added support for deploying MCP servers (making functions discoverable to MCP-compatible agents) - modal.web_endpoint and ASGI support makes Modal-hosted services callable from agents - There is no built-in "agent registry" or discovery mechanism; discoverability is handled at the application layer

Vercel: Sandbox, VM & Compute Features for AI Agent Workloads

Research sourced directly from Vercel's official documentation at vercel.com (as of April 2026).

1. VM Startup Speed / Cold Start Times

Vercel does not publish a specific millisecond figure for cold start times in its documentation. What is documented:

  • Archived functions (those not invoked within 2 weeks for production deployments, or 48 hours for preview deployments) experience a cold start that adds "at least 1 second longer than usual."
  • Edge runtime cold starts are described as near-instant because it runs on V8 isolates without requiring a container or virtual machine.
  • Node.js/Fluid compute cold starts are mitigated through two mechanisms:
  • Bytecode caching (Node.js 20+): Pre-compiles JavaScript bytecode after first execution so subsequent cold starts avoid recompilation. Only active in production environments.
  • Pre-warmed instances: On paid plans in production, Vercel keeps a minimum of one active function instance running, preventing cold starts entirely under normal traffic.
  • Fluid compute's optimized concurrency reuses existing instances for concurrent requests, significantly reducing the rate at which new cold starts occur.

The docs explicitly say: "By their very nature of being on-demand, serverless applications will always have the notion of cold starts" - but Fluid compute's concurrency model minimizes how often they happen.

Edge runtime: Must begin sending a response within 25 seconds; can stream up to 300 seconds total.

2. Boot Disk Access

No persistent boot disk. Vercel Functions have: - A read-only filesystem (the deployment bundle). - A writable /tmp scratch space of up to 500 MB. - Filesystem state (temp files, memory caches) is preserved when a function instance is reused (warm), but not across cold starts. - Bundle size limit: 250 MB (gzip compressed) for most runtimes; 500 MB for Python.

There is no concept of a persistent, rebootable disk image. The isolation boundary is a microVM (for traditional serverless) or a shared process (for Fluid compute).

3. Reboot Support

Not applicable in the traditional sense. Vercel functions are stateless and ephemeral. There is no reboot mechanism. The closest concepts:

  • Functions are archived when idle and unarchived (cold-started) on next invocation.
  • Instant Rollback lets you revert to a previous deployment quickly.
  • Fluid compute with the waitUntil API allows background tasks to continue after a response is sent, but there is no "reboot" of a running instance.
  • Vercel Workflow (beta) supports durable workflows that can pause, resume, and survive deployments/crashes through deterministic replay - the closest thing to long-lived stateful compute. Workflow steps can sleep for "minutes or months."

4. VM Forking Capability

Not supported. Vercel does not expose any forking API for VM instances. The isolation model is:

  • Traditional serverless: Each function invocation gets its own microVM.
  • Fluid compute: Multiple concurrent invocations share a single process/instance (in-function concurrency), but there is no user-controlled forking.
  • No snapshotting or cloning of running VM state.

5. Full Linux Support

Partial, not full. Vercel Functions run in a managed Linux environment but with significant restrictions:

  • Node.js runtime: Full Node.js API coverage, all standard Node.js APIs available.
  • Edge runtime: V8 isolates - NOT a full Linux environment. No filesystem access (not even /tmp), no require(), no native Node.js APIs beyond a short whitelist (async_hooks, events, buffer, assert, util). No eval or dynamic code execution.
  • No raw shell access, no arbitrary Linux process execution.
  • No WebSocket server support.
  • File descriptors limited to 1,024 shared across concurrent executions.
  • Vercel notes this is "neither a Node.js nor browser application" for the Edge runtime.

The Node.js runtime is essentially a Lambda-style environment (AWS Lambda is the underlying infrastructure, as evidenced by the blocked AWS_LAMBDA_* environment variables).

6. GPU Support

No native GPU support documented. Vercel's own compute (Vercel Functions, Fluid compute, Edge runtime) does not offer GPU instances.

For GPU workloads, Vercel's AI integration marketplace lists third-party GPU-enabled providers: - fal: "A serverless AI inferencing platform for creative processes" (GPU inference via integration) - Together AI, Replicate, DeepInfra: Third-party GPU inference services connectable via Vercel Marketplace integrations - Groq: LPU-based inference

These are API integrations, not GPUs running inside Vercel's own infrastructure.
