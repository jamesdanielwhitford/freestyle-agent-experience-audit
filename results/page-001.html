What sandbox providers let you fork a running VM? Like, duplicate it mid-execution?

Assistant2026-04-07T11:57:51.036Z

A few providers support VM/sandbox forking (snapshotting mid-execution and branching from that state):

Cloud/VM platforms

  • Firecracker (AWS) - supports snapshots of microVMs mid-execution; used internally by Lambda. You can restore multiple instances from the same snapshot, effectively forking.
  • QEMU/KVM - savevm/loadvm commands snapshot running VMs; you can restore the same snapshot multiple times to get parallel forks.
  • Vagrant - snapshot support via vagrant snapshot save/restore, works with VirtualBox and VMware backends.

Sandbox-specific

  • gVisor - supports checkpointing (CRIU-based), though forking from a checkpoint is more manual.
  • Kata Containers - built on Firecracker/QEMU, inherits their snapshot capabilities.
  • CRIU (Checkpoint/Restore in Userspace) - Linux tool for checkpointing processes or containers mid-execution and restoring multiple copies.

Higher-level / hosted

  • Modal - supports snapshotting container state for fast cold starts, though forking for parallel execution isn't a first-class API.
  • E2B - sandboxes are designed for short-lived execution; no native fork/clone API.
  • Dagger - pipeline execution with layer caching, not true VM forking but reuses cached states.

Best fit depends on your use case: - True parallel VM forking from a snapshot: QEMU/KVM or Firecracker - Process-level forking on Linux: CRIU - Hosted/managed with snapshot semantics: Modal is closest

## Overview of CRIU

CRIU (Checkpoint/Restore In Userspace) is a Linux software that can freeze a running container or application and checkpoint its state to disk, with the saved data used to restore the application exactly as it was during the time of the freeze.

## Checkpoint and Restore Process

CRIU captures everything about a running process including memory contents, open files, network connections, and process tree structure. Unlike traditional container stop and start operations that reinitialize applications from scratch, restore brings containers back to their exact previous state, with applications continuing from the instruction they were executing when checkpointed.

## Fork and Process Tree Handling

During restoration, CRIU calls fork() many times to re-create the processes needed to be restored. To checkpoint a process tree (a process and all its child processes), CRIU checkpoints each connected child process, meaning CRIU always checkpoints and restores a parent process and all its child processes.

## Container Integration (2026)

Kubernetes 1.25 introduced built-in forensic container checkpointing as an alpha feature, enabling checkpoint creation via kubectl without manual runc commands. CRIU is currently used by OpenVZ, LXC/LXD/Incus, Docker, Podman, Kubernetes and other software, and is packaged for many Linux distributions.

Based on the search results, here's information about Firecracker microVM snapshot, fork, and clone functionality for running instances:

## Snapshot Overview

MicroVM snapshotting is a mechanism through which a running microVM and its resources can be serialized and saved to an external medium in the form of a snapshot. This snapshot can be later used to restore a microVM with its guest workload at that particular point in time.

## How Snapshots Work

Firecracker exposes a create_snapshot function that yields two files: snapshot.snap — the configuration of the machine (CPU template & count, disks attached, network devices attached, etc.) and memory.snap — the memory of the VM while it was paused. These two files, together with the disk, contain everything needed to start a MicroVM, and it will just continue from when the snapshot was taken.

## Cloning and Forking Running Instances

A Firecracker microVM snapshot can be used for loading it later in a different Firecracker process, and the original guest workload is being simply resumed. This capability enables cloning running VMs. When calling create_snapshot on the Firecracker VM, it takes about 1 second per gigabyte to write the memory snapshot file. Meaning that if you have a VM with 12GB of memory, it would take 12 seconds to create the snapshot.

## Limitations for Clones

Guest network connectivity is not guaranteed to be preserved after resume. For recommendations related to guest network connectivity for clones please see Network connectivity for clones. Additionally, both network and vsock packet loss can be expected on guests that are resumed from snapshots in another Firecracker process. It is also not guaranteed that the state of the network connections survives the process.

## Overall Approach

CodeSandbox allows people to click "fork" and get an exact copy of that environment within 2 seconds, and it clones a VM in under 2 seconds (average 921ms in published benchmarks) using copy-on-write memory sharing, with the clone preserving full process state so running dev servers and databases continue in the forked sandbox without restart.

## The Technical Challenge

The core challenge is handling large memory files. CodeSandbox's goal is to create a clone within 2 seconds, and since they're working with big files (4GiB-12GiB), they cannot serialize and copy the file within that time.

## The Solution: Two-Part Approach

CodeSandbox overcomes this by eagerly saving memory changes to the disk so that when they need to serialize the memory, most of it has been done already, and by using Copy-on-Write for copying the file, only copying the memory blocks when they're actually needed by the new VM.

## Evolution to userfaultfd

Later, after enabling a new UFFD handler, their live Copy-on-Write forks became instant and the dev server of clones became available within 2 seconds, and CodeSandbox can now clone the memory of VMs in a Copy-on-Write fashion without having to go through the filesystem. They can now reliably fork a VM within 1.5s, regardless of how much memory is used for the VM.
